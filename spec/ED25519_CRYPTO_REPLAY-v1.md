# AIFC Ed25519 Cryptographic Replay v1

Status: **NORMATIVE DRAFT / VERIFIER A v0.6**

This profile defines the cryptographic verification step that follows successful `AIFC-ED25519-DIRECT-TYPED-V1` preimage reconstruction.

It establishes only:

```text
this exact 64-byte Ed25519 signature
is mathematically valid over
this exact frozen AIFC signature preimage
under this exact 32-byte public key
resolved from this exact signing registry snapshot
```

It does **not** establish historical key safety, external freshness, causal validity, target-source validity, statistical admission, or any physical mechanism.

## 1. Admission order

Verifier A v0.6 uses the order:

```text
exact evidence bytes
  -> canonicalization
  -> content identity
  -> Draft 2020-12 runtime schema
  -> receipt/quorum semantic binding
  -> exact typed signature preimage reconstruction
  -> signing registry resolution
  -> registry-local key eligibility
  -> Ed25519 cryptographic verification
  -> later historical key/freshness gates
```

No crypto success may repair an earlier semantic or evidence failure.

## 2. Registry-local key eligibility

For each `SignaturePreimageMaterial`, the verifier resolves the exact `AIFC/witness-registry/v1` named by the signed `registry_hash`.

It MUST independently verify at least:

```text
registry.registry_sequence == signed registry_sequence
exactly one matching witness_id exists
witness status at that registry snapshot permits signing
exactly one matching key_id exists for the witness
key.algorithm == Ed25519
key.public_key_encoding == hex
key.public_key is exactly 32 bytes / 64 lowercase hex chars
key status at that registry snapshot permits signing
valid_from_registry_sequence <= signed registry_sequence
signed registry_sequence <= valid_until_registry_sequence, when bounded
```

The public key bytes used by the crypto backend come only from that resolved registry object.

A claimant-supplied alternate public key MUST NOT be substituted at verification time.

## 3. Cryptographic operation

The mathematical operation is direct Ed25519 verification over the raw typed preimage bytes produced by `SIGNATURE_PREIMAGE_PROFILE-v1`.

There is no additional protocol prehash.

Conceptually:

```text
Ed25519.Verify(
    public_key_32_bytes,
    exact_signature_preimage_bytes,
    signature_64_bytes
)
```

The canonical external representations remain:

```text
public key = 64 lowercase hex characters
signature  = 128 lowercase hex characters
```

## 4. Verifier A backend

Verifier A v0.6 uses the system OpenSSL Ed25519 implementation through `pkeyutl -verify -rawin`.

The raw 32-byte public key is wrapped deterministically as the RFC 8410 Ed25519 SubjectPublicKeyInfo form before being passed to OpenSSL.

The verifier result records:

```text
crypto_backend.backend_id = OPENSSL_PKEYUTL_ED25519_V1
crypto_backend.version_line
crypto_backend.executable_sha256
```

This fingerprint is reproducibility evidence. It is not a proof that OpenSSL is bug-free and it is not a substitute for independent Implementation B.

A backend error or non-verifying signature fails closed.

## 5. External known-answer anchor

The Verifier A corpus includes an RFC 8032 Ed25519 known-answer vector. The verifier must accept the published valid signature and reject at least:

```text
message bit flip
signature bit flip
wrong public key
```

This prevents the crypto tests from relying only on signatures generated by the same AIFC fixture code.

## 6. AIFC typed-preimage bridge

A separate integration vector constructs the normative 381-byte AIFC trial receipt preimage with diagnostic SHA-256:

```text
2c2ad0fd73ebac49a048038941fc4cae0b616cb8ef8a7b174acc63c7c63b1297
```

The deterministic test key signs those raw bytes and Verifier A resolves the registry key and verifies the signature.

The SHA-256 above remains a test-vector fingerprint only. It is not the Ed25519 message prehash.

## 7. Required attacks

The v0.6 crypto corpus must reject at least:

```text
ED25519_SIGNATURE_BIT_FLIP
ED25519_MESSAGE_TAMPER
ED25519_WRONG_PUBLIC_KEY
KEY_ID_SUBSTITUTION
WITNESS_ID_SUBSTITUTION
REGISTRY_SEQUENCE_REBINDING
KEY_NOT_YET_VALID_AT_REGISTRY_SEQUENCE
KEY_EXPIRED_AT_REGISTRY_SEQUENCE
KEY_REVOKED_IN_SIGNING_REGISTRY
KEY_COMPROMISED_IN_SIGNING_REGISTRY
WITNESS_NOT_ACTIVE_AT_SIGNING_REGISTRY
```

The earlier signature-preimage attack corpus remains mandatory.

## 8. Historical key lifecycle is a different problem

A signature may be mathematically valid and the key may have been `ACTIVE` in the signing registry snapshot, yet later evidence may establish that the key was compromised at or before the signed position.

Therefore:

```text
REGISTRY_LOCAL_KEY_ELIGIBILITY = PASS
ED25519_SIGNATURE_CRYPTO       = PASS
```

MUST NOT imply:

```text
HISTORICAL_KEY_LIFECYCLE = PASS
```

The next protocol layer must represent compromise/revocation lifecycle events and an externally rooted earliest uncertainty/effective boundary, then determine which historical certificates require invalidation or downgrade.

## 9. Freshness remains separate

Likewise:

```text
valid signature != fresh history
```

A valid cryptographic receipt can belong to a stale but internally consistent rollback snapshot. `EXTERNAL_FRESHNESS_REPLAY` remains a separate mandatory gate.

## 10. Claim ceiling

Even after successful v0.6 crypto replay:

```text
HISTORICAL_KEY_LIFECYCLE = BLOCKED
EXTERNAL_FRESHNESS_REPLAY = INCOMPLETE
CAUSAL_D_SEPARATION = BLOCKED
TARGET_SOURCE_CRYPTOGRAPHIC_PROOF = BLOCKED
FULL_STATISTICAL_REPLAY = BLOCKED
IMPLEMENTATION_A_PASS = NOT_ESTABLISHED
AIFC_V1_FROZEN = FALSE
PHYSICAL_RETROCAUSALITY = NOT_OBSERVED
```

If a downstream component attempts to emit a forward-null admitted result while historical key lifecycle is blocked, v0.6 MUST cap the terminal grade to `NOT_ADMITTED`.
